## 1. The threat model on one page

Terms used throughout. **Google Workspace** is the organisation's mail, directory and collaboration tenant; **Super Admin** is its role with every administrative power, which Google cannot limit to part of the organisation or to a subset of powers. A **Google Cloud organisation** is the tree of folders and projects the agents run in; **Organization Administrator** is its top role. A **service account** is the identity a program normally uses in Google Cloud; it can hold any Workspace admin role except Super Admin, which is why Wall-E is a user account, `walle@`. An **action service** is the deterministic code that holds the credential, decides, audits and executes; the language model never touches the credential. An **OAuth client** is the application record under which `walle@` consents once to a listed set of permissions (scopes), producing a **refresh token** the action service stores and exchanges for **access tokens** that live up to an hour (`Assumption:`). **Domain-wide delegation** lets a program act as any user in the tenant; the platform grants it to nothing, ever.

The objective as stated on 2026-09-13 and the two Google facts that fix its consequences — a service account cannot be Super Admin, and Super Admin cannot be scoped — are on [../01-hld.md "What this reverses and what it costs"](../01-hld.md#what-this-reverses-and-what-it-costs). What follows is the loss table of that page read as a threat model.

| Threat | What it reaches | What stops it (enforced) | What sees it (detected) | Residual, unsoftened |
|---|---|---|---|---|
| **A leaked robot credential** — a refresh or access token of `walle@` used outside the two action services | **The whole tenant**, and through the Admin console's power to grant Organization Administrator, a path into the Google Cloud organisation including `EVE_PROJECT`, `MO_PROJECT` and the core projects | Nothing stops a stolen refresh token from working. Before the leak: custody (two hardware keys, named custodians, witnessed record, no interactive login). ## 2. Enforced versus detected: the rule and the six containment primitives

Every control is either **enforcement-grade** (Google or the platform refuses the action; the verdict is produced outside the agent's own process; a failure of the control stops the action) or **detection-grade** (the action happens and something independent sees it within a stated latency). **Nothing detection-grade may stand alone in a safety argument.** A probabilistic content screen is never a trust boundary whatever its grade ([../01-hld.md §0.2](../01-hld.md#02-the-six-containment-primitives-and-how-each-is-graded)).

| # | Primitive | Mechanism | Grade |
|---|---|---|---|
| CP1 | A trust boundary the agent cannot redraw | Resource Manager folders, organisation policy, the factory's CI identity, Privileged Access Manager (PAM: time-boxed, justified, logged elevation with no self-approval) | enforcement |
| CP2 | Autonomy as data; humans raise, machines lower | `agent-manifest.yaml`, `ladder.schema`, `audit.schema`; promotion by pull request with evidence a validator recomputes | enforcement, in the action service |
| CP3 | A capability ceiling outside the agent's process | The model holds no credential; the action service is the only holder; ceilings are code plus the folder deny policy, the Principal Access Boundary and the OAuth scope set | enforcement |
| CP4 | A fleet kill switch outside any agent project | One organisation-policy flip and one deny rule stop every agent principal; drilled monthly | enforcement |
| CP5 | A model-free monitor with halt authority | No model on the path that approves, halts, demotes or vetoes; a project-level service denial keeps the model API out of `EVE_PROJECT`; CI forbids a model client in the image | enforcement, by absence |
| CP6 | Evidence the judged thing cannot forge or silence | Organisation-level sinks into a locked bucket, the SIEM export, the witness organisation, an absence alarm | **detection**, with an absence alarm |

For the super-admin tier the design says, rather than pretends otherwise, that **detection is the primary control**: the Workspace-side refusal that bounded the old custom role is gone, the action service is the one enforcement point left, and the consented scope set is the only Google-enforced ceiling. Three Google facts are kept out of every safety case until a test answers them: whether the Principal Access Boundary blocks Cloud Run invocation (P60: it does not), whether the Admin console access level applies to super admins (P7, open), and the deny policy's spelling of the agent principal set (P8, a spike) ([../01-hld.md §16](../01-hld.md#16-what-the-platform-does-not-do)).

## 3. The kill switches K0–K7

Eight switches, from surgical to total, from [../../wall-e/ARCHITECTURE.md §4.6](../../wall-e/ARCHITECTURE.md#46-kill-switches) and [../04-identity-and-privileged-access.md §9.7](../04-identity-and-privileged-access.md#97-how-k7-sits-with-each-agents-k0k6). Every target is a design target; nothing has been measured, because nothing is built.

| Switch | Mechanism | Who pulls it | Target | What it does not stop |
|---|---|---|---|---|
| **K0** halt writes | `POST /v1/control/halt` on the action service | Any operator, Eve, or a breaker; no approval | Under 5 s at the endpoint; containment under 60 s from the decision | Reads; an item already inside a Workspace API call |
| **K1** demote one cell | `/v1/control/demote` for one family-and-trigger pair | Any operator, Eve, or a breaker | Under 5 s | Every other cell keeps its level |
| **K2** stop new runs | Pause the Scheduler jobs, detach the push subscriptions | An operator with the Google Cloud rights | Seconds | Runs already open; chat requests in flight |
| **K3** cut the agent off | Remove `run.invoker`, the IAM role that lets an identity call a Cloud Run service (the managed container service the action services run on), from the reasoning layer's identity | A project IAM administrator | About a minute | What the action service is already executing; operator control endpoints keep working, deliberately |
| **K4** kill the credential | The action service revokes its own refresh token at Google, on both services | Any operator, one call to each service; no console, no second person | Seconds | **An access token already issued stays valid for up to 60 minutes** (`Assumption:`); recovery is a full re-bootstrap |
| **K5** revoke the grant or suspend the robot | `tokens.delete` for both client ids, or `users.update` with `suspended: true` on `walle@` | A human Workspace super admin other than the robot, on the two-person rota, paged from the witness | Within 30 minutes of a severity-1 acknowledgement (`Assumption:`) | The same 60-minute access-token residual |
| **K6** remove Super Admin from the robot | `users.makeAdmin` with `status: false`, or the Admin console | Human only, on the K5/K6 rota; never the agent owner when the actor is the owner | Within 60 minutes | Anything already executed; Google Cloud reach already obtained. **The switch that survives a token already minted** (`Assumption:` each Admin SDK call is authorised against the account's current privileges; verified at the first K6 drill) |
| **K7** fleet kill | Four pre-written levers at the tier folders in the order KF-1 (service denial), KF-3 (Scheduler pause), KF-4 (Principal Access Boundary), KF-2 (deny policy) | `platform-approvers@` through a PAM entitlement, or the deterministic job `k7-executor@CORE_PROJECT` on a severity-1 SIEM rule; **never a model** | KF-1 under 60 s; under 5 minutes end to end | `fld-controllers`, `fld-platform-core` and `fld-gemini-enterprise` (P70): Eve keeps watching and paging. Lifting K7 is a two-human pull request |

Who may pull what, by role, from the incident RACI ([../07-monitoring-detection-incident-response.md §9.1](../07-monitoring-detection-incident-response.md#91-roles-and-raci)): K0 and K1 are a stop anyone may pull without approval — any operator, Eve or a breaker, no incident opened by default; K2 to K4 are the platform owner's, with the agent owner; K5 and K6 belong to the on-duty human super admin on a two-person rota with the second human, ordered by the incident commander, and the agent owner never pulls them on an incident where the actor is the owner; a hand-pulled K7 is the platform owner through the PAM entitlement with the security reviewer as second approver. K3 and above open an incident.

Three facts to hold onto. **K0 is what stops work now; K4 is what stops the credential**; neither invalidates an access token already in hand. Under KF-1 the K0 and K4 endpoints are themselves refused, so **K4 is pulled before K7** in the P-SA runbook; the crisis order is K0 `halt_all` → K4 → K7 on the P-SA folder → K5 → K6 if the account itself is suspect → evidence preservation → the incident commander. And a machine-invocable stop on `walle@` is deliberately not built (P16, proposed "none now"): an automatic lock-out is also a path a compromised monitor could pull ([../12-open-decisions.md §4](../12-open-decisions.md#4-before-the-super-admin-grant)).

One open point security must settle before the grant: whether K6 is a one-person or a two-person act. Page 04 gives K6 to one human super admin within 60 minutes; the full build's gate file says the other super admin approves it under Workspace multi-party approval, and page 04 itself records that whether `makeAdmin` is covered by that approval is an `Assumption:` to verify on the sandbox tenant ([../04-identity-and-privileged-access.md §8.4](../04-identity-and-privileged-access.md#84-workspace-multi-party-approval-the-two-person-rule-google-enforces)). The two readings have opposite consequences at 03:00, and the rota file must say which.

Drill cadence: K0–K3 every 30 days; K4 at commissioning and after any real credential incident; K5 and K6 quarterly on the sandbox tenant's robot twin, never in production; K7 monthly in nonprod. CI refuses any promotion citing a drill older than 30 days.

## 4. The thirteen compensations, as preconditions of the grant

All thirteen are preconditions of the super-admin grant, none deferred; the checklist the gate reads is [../11-tisax.md §6.3](../11-tisax.md#63-compensations-as-preconditions--the-checklist-the-gate-reads). The failure rule is what makes the record a control rather than a confession: after the grant, any row turning red is a severity-2 finding with a 30-day window; two rows red at once, or row 5, 6 or 11 red at all, is severity 1 and the on-duty human super admin pulls **K6 until the row is green again** — the role exists only while its compensations do. Google's own guidance — super admins few, human and not for daily use — will be cited by the assessor; the record answers it by confining the robot's daily use to band A and band B, every action attributable to a human prompt or a catalogued trigger, and by the permanent ceiling of row 9 ([../11-tisax.md §6.1](../11-tisax.md#61-what-the-deviation-is-in-isa-terms)).

| # | Precondition | Owner | Verified by | Red when |
|---|---|---|---|---|
| 1 | Three bands in code: A catalogued autonomous work on the narrow client; B uncatalogued super-admin work, permanently L3, two-person, chat only; C console-only work handed to a human | Wall-E owner | CI job output: `walle-actions` exposes `/v1/execute` only; `walle-actions-super` exposes `/v1/execute-generic` and `/v1/handoff` | Any playbook uses `SUPER` or `WRITE-generic` |
| 2 | The two lists signed (P29, open): hard-denied in every lane; reachable only through band B at tier `SUPER` | Wall-E owner; security reviewer | Denial-suite report; hash of the lists in the deviation file | Denial suite fails on "write targeting the robot itself" or "any `makeAdmin`" |

Two things the reader should know about this table. Rows 11 to 13 are the people and the paper the technical rows assume, not controls in the CP sense; an assessor will ask which of the two grades "enforcement (human)" on row 7 is, and the page owes that correction. And on the DPIA the pages disagree: the HLD's tier gate lists "the DPIA" among the grant preconditions, the checklist asks only that it has *started*, and GDPR Art. 35 requires the assessment before the processing; the DPO and the owner have to choose ([../brief/26-personal-data-and-employees.md](../brief/26-personal-data-and-employees.md#229-still-open)). The setup procedures split the gate (SD-02, P145): everything before the grant may be built with `privilege: super_admin_pending`; the gate refuses only the Super Admin assignment to `walle@`, and the enforceable refusal is the second human's on the day, since no CI can refuse an Admin-console act ([../12-open-decisions.md §6a](../12-open-decisions.md#6a-proposed-by-the-setup-procedures-p144p191)).

## 5. The credential story

Which identity holds what, from [../../wall-e/ARCHITECTURE.md §4.2](../../wall-e/ARCHITECTURE.md#42-the-principals) and [../09-supply-chain-secrets-recovery.md §2.4](../09-supply-chain-secrets-recovery.md#24-the-cryptography-table--every-key-and-secret-on-the-platform). **Secret Manager** is Google's store for secrets, regional here, with one reader per secret and a pinned version number, never `latest`. **HSM** keys are hardware-backed keys in Google's key service.

| Identity | Type | Holds | Must never |
|---|---|---|---|
| `walle@` | Workspace user, licensed, **Super Admin** (P33); two hardware keys with named custodians; a Workspace identity, never a Google Cloud caller | Nothing itself: its two refresh tokens live in Secret Manager. Its reach on the Google side is bounded only by each client's consented scopes | Be signed into interactively after bootstrap (severity 1); be the only or the recovery super admin; be the target of any write through its own lanes; be a multi-party approver |
| `walle-actions@` | Service account, `WALLE_PROJECT`; runs band A | The **narrow** client's refresh token, the narrow OAuth client, an HMAC key (a shared secret for signing confirmations); Eve's public key pinned as a PEM file (the text form of a public key) | Read Eve's private key; mint an Eve approval; delete audit rows; read the broad client |
| `walle-actions-super@` | Service account, `WALLE_PROJECT`; runs bands B and C | The **broad** client's refresh token and client, nothing of the narrow pair | Read the narrow client; execute at tier `SUPER` without a second human super admin; serve any trigger but a human in chat |
| The reasoning layer (`walle-agent@`, or Agent Identity — a keyless Google-issued identity expiring daily) | The identity the model runs under | Nothing; `run.invoker` on the execute and plan endpoints only | Read any secret; reach any control or approval endpoint; hold a Workspace token |
| `eve@` | Workspace user with a **read-only custom role**, never Super Admin | One OAuth client, one refresh token with read-only scopes | Execute a Workspace write; read any Wall-E secret |
| `eve-controller@EVE_PROJECT` | Eve's gate identity | `cloudkms.signer` on the HSM key `eve-approval`; cross-project `run.invoker` for approve, veto, halt, demote | Raise a level; hold a model client; share a key with any Wall-E principal |
| `eve-export@EVE_PROJECT` | Eve's export job | Exactly two create-only, resource-level grants on witness resources | Delete or rewrite anything in the witness |
| Mo's identities | `MO_PROJECT` | Dataset reads and two read endpoints; **no credential, no secret, no invoker, no signer** | Write to any repository; open its own pull request (a bot identity that is not Mo does) |
| The CI deployer, `<agent>-deployer@<agent project>` | Per-agent deploy identity | No key: impersonated per release run through workload identity federation (keyless impersonation from the CI system, with no stored credential); the only principal with `run.services.create/update` in its project outside PAM | Be held by any operator; deploy another agent's project |

**OAuth clients and the consent.** Exactly one interactive sign-in is unavoidable: the robot consents once to each of the two clients, in one witnessed sitting, repeated only on rotation or a scope change. Scopes freeze at consent time, so each consented set is the true maximum reach of that token if it leaks ([../../wall-e/ARCHITECTURE.md §4.3](../../wall-e/ARCHITECTURE.md#43-the-one-time-consent-flow)). A token minted to `walle@` from any client other than the two committed ids is itself detection rule SA-05.

**What makes a refresh token die**, each an operational rule and each applying to the narrow and the broad token independently: an external consent screen left in testing (seven days), more than 100 live tokens per client, six months unused, a password change while Gmail scopes are granted, a requested service set to restricted in API controls, and revocation (as recorded on 2026-09-13, to be re-verified). `invalid_grant` from Google is a paging incident, never a retryable error ([../../wall-e/ARCHITECTURE.md §4.4](../../wall-e/ARCHITECTURE.md#44-what-makes-the-credential-stop-working)).

**What revocation stops, and when.** K4 and K5 stop future token refreshes; they do not invalidate an access token already in hand, which lives up to an hour (`Assumption:`). Disabling the secret is not a kill switch: a container that caches its API clients never re-reads it, and `latest` falls back to the previous enabled version. Only revocation at Google stops a running instance now, which is why a K4 drill attempts a Workspace read from a warm instance immediately afterwards — a success means a cached token was measured, not a kill switch. K6 is the switch that survives a minted token, because the token outlives the privilege.

**The two-person rule Google enforces.** Workspace multi-party approval — a second administrator must approve changes to sensitive settings — is on for every covered setting before the grant (P66): role assignment and custom-role privilege updates, domain-wide delegation, 2-Step Verification, session control, login challenges, account recovery, SSO, Context-Aware Access. It is the only Google-enforced two-person rule over the robot's credential. It does not cover `users.delete`, OU moves, sink settings or activity rules; those stay code-refused and detected. The robot is never an approver; "multi-party approval off" is hard-denied, and an approval whose actor is `walle@` is severity 1 ([../04-identity-and-privileged-access.md §8.5](../04-identity-and-privileged-access.md#85-the-two-person-rule-for-the-privileged-tier-in-one-table)).

**No domain-wide delegation, ever**, to anything on the platform: a compromised delegate could act as anyone including a super admin. The super-admin roster in steady state is exactly three — `sa-1-admin@`, `sa-2-admin@` (outside the Wall-E line) and `walle@` — with self-recovery off at the top OU (P68).

## 6. Detections and the incident path

**SIEM** is the security information and event management service that collects logs, runs detections and has a desk that acknowledges pages; **MDR** is a managed detection and response retainer that watches round the clock. Google SecOps in the EU is proposed as the SIEM, or the organisation's own if it meets the contract's nine requirements (P10, open). The nine clauses (S1–S9): EU residency; retention at or above 400 days; the four organisation-owned feeds with no domain-wide delegation and no service-account key; detection-as-code with a fixture per rule; a case system; a 24x7 desk; an outbound authenticated REST call to the fleet-kill job; keying on the four entity types (agent principal, robot user, OAuth client id, operator); reader access through a group the platform does not administer, with no reader for any agent principal ([../07-monitoring-detection-incident-response.md §2.1](../07-monitoring-detection-incident-response.md#21-why-the-decision-is-a-contract-first)). The design does not run a SOC; it buys acknowledgement for Tier P and runs Google's detections for the rest. `Assumption:` if the organisation has a SOC, the platform feeds it.

**The catalogue is code**, owned by IT security, one fixture per rule as a merge condition (P96; [../07-monitoring-detection-incident-response.md §6.2](../07-monitoring-detection-incident-response.md#62-the-super-admin-set-workspace-side--siem-hosted-severity-1-owned-by-it-security), [§6.3](../07-monitoring-detection-incident-response.md#63-the-super-admin-set-gcp-organisation-side--the-reach-into-the-organisation)):

| Set | Rules | What they watch | Severity |
|---|---|---|---|
| SA-01..SA-09 | Workspace side | A robot method outside the allow-list with no band-B row; any `makeAdmin` by anyone; posture changes by any actor; any interactive login on `walle@` or `eve@`; a token from a foreign client; the daily roster diff; a robot event with no audit row; an application the robot never needs; control-group membership | 1, all |
| SG-01..SG-07 | Google Cloud side | Organisation, folder and core-project IAM; sinks and audit configs; policies, floors and K7 levers; project deletion; PAM grants; Google-personnel access (severity 2); deploys on a credential holder outside CI | 1, except SG-06 |
| PL-01..PL-15 | Platform-wide | Heartbeat absence; foreign principals; secret access by a non-reader; Model Armor rates and floor writes; gateway policy; break-glass; evidence-store state; Access Approval; attestations | 1 to 3 |

## 7. Supply chain

The principle: the agent never writes to a repository, a registry, a deploy identity, its own ladder or its own ceilings; the pipeline that does write is a keyless CI identity whose every output is signed, scanned and admitted by a policy the agent's owner cannot edit ([../09-supply-chain-secrets-recovery.md §1.1](../09-supply-chain-secrets-recovery.md#11-the-path-from-commit-to-running-digest)). **Binary Authorization** is Google's admission control that refuses a container revision without the required attestations; **Agent Runtime** is the managed service the reasoning layer runs on.

## 8. Eve's independence, honestly, and the witness organisation

Eve is two paths. The **control path** (`eve-gate`, `eve-reconciler`, `eve-console` in `EVE_PROJECT`) approves, vetoes, halts and demotes over plain authenticated REST with the HSM key `eve-approval`, and is deterministic by absence: a project-level service denial keeps the model API out of `EVE_PROJECT`, and CI forbids a model client in the image. The **reporting path** (`eve-advisor`) may reason but is report-only by construction: it writes narratives and advice, holds no signer, invoker or secret, nothing it writes is read by the gate or any action service, and it pages at severity 2 only ([../01-hld.md §13.2](../01-hld.md#132-eve--independent-controller-two-paths-a-witness-outside-the-tenant-a-second-human)).

**The honest statement, carried in every attestation**: a Workspace super admin can grant themself Organization Administrator on the tenant's Google Cloud organisation, `EVE_PROJECT` is inside it, and so **Eve's independence inside the organisation is detective, not structural** ([../../eve/01-hld.md §1](../../eve/01-hld.md#1-eves-independence-detective-inside-the-organisation-structural-through-the-witness)). The credential can suspend `eve@`, revoke Eve's token, remove Eve's role, switch off "Share data with Google Cloud services" and re-filter the organisation sinks; only code and detection stop it.

| Part | Against whom | Grade |
|---|---|---|
| The project boundary: Eve's key, secrets, dataset, evidence and config in `EVE_PROJECT`; no Wall-E deployer holds a role there or on the folder | Wall-E's project owners, deployers and service identities | enforcement |
| The same boundary against the super-admin credential | `walle@` and any human super admin who reaches Organization Administrator | **detection only**, through SA-*, SG-*, Eve's tenant-integrity rules and the absence alarms |
| **The witness organisation** `org-witness`: a second organisation on a separate, minimal Cloud Identity tenant (P14, open; `Assumption:` Cloud Identity Free on a distinct domain) holding the daily append-only mirror of Eve's findings, verdicts, incidents and pages, the evidence copy, the K5 rota records, the severity 1 and 2 channels to individuals and the absence alarm | Everyone in the tenant, its super admins included | enforcement, outside the tenant |

What makes the witness structural: it receives a **push, never a pull**, by `eve-export@` through exactly two create-only, resource-level grants on witness resources; its two super admins are IT security people who are neither tenant super admins nor the platform owner, second human or second operator (SD-04, P147); no witness principal holds any grant in the tenant's organisation. It sees the deletion of `EVE_PROJECT` within fifteen minutes and the absence of evidence. **It does not see the forgery of an approval.** The only mechanism that stops a super admin who reaches Organization Administrator from forging an approval or undoing a kill is relocating Eve's control path — gate, HSM key, console — to the witness when IT security operates it: the end state P15, proposed, dated now, built later, gating Tier X and not the grant.

Two limits security should test rather than inherit. Eve reads the plan from the service it is checking; recomputing the hash, re-reading every target with its own credential and corroborating the trigger against Google's log means a lie must be consistent across four surfaces, but the "shows plan A, executes plan B" case is bounded at one batch, not closed ([../../eve/06-failure-modes.md "Five named limits"](../../eve/06-failure-modes.md#five-named-limits-on-eves-independence)). And Eve's BigQuery tables cannot be made insert-only — no such permission exists — so row tampering is made detectable, not impossible: a severity-1 rule on DML against Eve's tables and per-table row counts in the witness heartbeat, an accepted limit the security reviewer ratifies (SD-43, P186). A compromised Eve gains halt and demote — a denial of service a human clears in seconds — and signing only for cells already marked binding, within the envelope's lifetime; never a level raise, a Workspace write or its own thresholds ([../../eve/06-failure-modes.md "When Eve is compromised"](../../eve/06-failure-modes.md#when-eve-is-compromised)).

In the proof of value and the three-day build Eve has no witness and lives inside the reach of the administrators it watches; both forbid the sentence "Eve is independent" (§9).

## 12. The verdict of the cross-check review of 2026-09-18, and what it refuses today

The design and the three build paths were cross-checked on 2026-09-18 against the objective of 2026-09-13; the security part of that review stood in the seat of the security reviewer who would sign the deviation record, and its verdict is on the review page ([the cross-check review of 2026-09-18, §4 "Security"](../14-crosscheck-review.md#4-security)). What it says, and where each point is defined:

- **The stance holds.** On every page that matters the design says that a super-admin robot moves the platform from "Google refuses" to "code refuses and detection watches", that Eve's independence inside the tenant's organisation is detective and only the witness organisation is structural, that a leaked token is a tenant compromise with a path into the Google Cloud organisation including `EVE_PROJECT` and `MO_PROJECT`, and that the deviation is carried by thirteen compensations of which several are organisational, not technical ([../01-hld.md "What this reverses and what it costs"](../01-hld.md#what-this-reverses-and-what-it-costs); [../../eve/01-hld.md §1](../../eve/01-hld.md#1-eves-independence-detective-inside-the-organisation-structural-through-the-witness)). The two grades are two words used as two words, and the three open Google facts (P7, P8, P60) are kept out of the safety case rather than counted ([../01-hld.md §16](../01-hld.md#16-what-the-platform-does-not-do)).
- **Enforced:** the OAuth scope split and the absence of `cloud-platform`; no domain-wide delegation, ever; IAM-only invocation with no human or group on any credential holder; Binary Authorization on every Cloud Run credential holder in the full build; the folder deny policy, and the Principal Access Boundary for engine queries; a project-level service denial that keeps a model out of Eve's control path; PAM's approver-is-not-requester; Workspace multi-party approval on role assignment; the write-ahead audit, the forced dry run and the hard-denied list as code in the action services (§2, §5, §7 above).
- **Detected and nothing more:** every use of the robot's credential outside the two action services; every act of a super admin against Eve, the sinks, the audit configuration or the evidence stores inside the tenant's organisation; Agent Runtime engine drift; secret access by a non-reader; row tampering in Eve's BigQuery tables, since no insert-only permission exists (§6, §8 above).
- **Accepted and written down:** risk row R-01, bounded by custody, scope split and detection latency, with a token valid for up to an hour after suspension (`Assumption:`); the one-batch "shows plan A, executes plan B" residual; a compromised Eve signing inside an existing envelope; Mo's truthful-but-tendentious pull request; Agent Runtime's lack of an admission hook; one region; invisible Google-side tenancy segregation; some stores on Google-managed keys; one model family across the fleet (§11 above).
- **Refused today,** by the security reviewer role the review stood in for: the deviation record itself, because rows 5 (the SIEM with 24x7 acknowledgement, the witness), 8 (the P3 perimeter spike) and 11 (a second human outside the administration line) of the gate checklist are not green ([../11-tisax.md §6.3](../11-tisax.md#63-compensations-as-preconditions--the-checklist-the-gate-reads)) and rows 1, 2, 4, 9 and 10 cannot be proven while the service code is BLOCKED ([../setup/README.md §8](../setup/README.md#8-blocked-index), B-16); the gate-day check of who can mint a token for the credential holders, because it omits the two approval-surface identities whose impersonation forges an approver the action service trusts ([../setup/38-super-admin-gate-and-grant.md](../setup/38-super-admin-gate-and-grant.md); X-25); and the three-day build's live block as written, because its halt lever is writable by the process it halts (X-33), its caller-account fallback lets one person request and approve (X-34), and its primary calling path depends on a gcloud behaviour the full build's own page says does not work for user credentials (X-35) — the unwind itself was carried on 2026-09-18 (§9 above). None of these is a flaw in the stance; each is a page that must change before the stance is true of what would be built.

The review's security findings are X-04 (the unwind, carried), X-24 to X-26 (the design pages against the full build), X-33 to X-37 (the three-day code and day files) and X-60 to X-63 (low, three-day), in [its §6](../14-crosscheck-review.md#6-findings-register); every row is `open` on 2026-09-18 until a later step verifies it. What it found sound is in [its §7](../14-crosscheck-review.md#7-what-is-sound): the loss table written before the compensations; two grades used as two words; a complete and bounded credential story; action services that cannot approve themselves; Eve's control path model-free by absence; silence as a halt; the grant as a gate; the smaller paths refusing the sentences that would mislead; and Mo unable to move anything. The regulatory state re-verified on 2026-09-18 and the dated path are in [its §5](../14-crosscheck-review.md#5-the-path-to-the-regulation) and in [compliance-and-regulation.md](compliance-and-regulation.md).
