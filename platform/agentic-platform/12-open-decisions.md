## 1. How this register works

**States.** `decided` — the named owner decided, on the date given. `closed` — answered by
a later row or by a verified fact; the row stays so the closing reference is not lost.
`proposed` — a detailed page proposed a value and recorded it; it stands, and the factory, the
validator and the runbooks are written to it, until the owner named in the row overturns it in
writing. `open` — nobody has decided and no page proposes beyond the HLD's recommendation; the
gate it blocks stays red. `spike` — decided by a test on a throwaway resource in nonprod, with
the pass criteria on the recording page; the spike's artefact closes the row.

**Who changes a row.** The owner of the row, in a pull request on this page, with the change
dated in the row. A row whose gate has passed is not reopened by editing it: it is superseded by
a new row that names it. Loosening a fleet default (P77) is a platform decision the security
reviewer signs, never a page edit.

**What "why it matters" answers.** The one thing that cannot be built, verified or defended
while the row is open — a factory input the pipeline refuses without, a safety case that rests
on an unverified name, an audit question with no evidence. If a row's "why" cannot be stated
that way, the row is a preference, not a decision, and it does not belong here.

**How a gate closes.** A gate is green when every row in its group is `decided`, `closed`,
`proposed` or a passed `spike`; an `open` row keeps the gate red. The admission gate (HLD
§5.3, [05](05-registry-and-autonomy-contract.md) §7) reads the tier gate's state, so a row left
open here is visible as a refused register row there, not as a forgotten paragraph.

**Numbering.** P1–P34 are the HLD's ids, unchanged. P35–P141 continue them in page order
(02: P35–P47; 03: P48–P59; 04: P60–P70; 05: P71–P80; 06: P81–P91; 07: P92–P103; 08:
P104–P114; 09: P115–P124; 10: P125–P132; 11: P133–P141). One HLD decision, P3, was refined by
page 06 without a new id; it keeps P3. New decisions append at P142; ids are never reused.

**Cross-references.** "Supersedes" means the platform row replaces the agent-set decision for
every agent, Wall-E included, and the propagation stage (HLD §18) adds the dated pointer line
in the agent set. "Depends on" means the platform row cannot pass its gate until that agent-set
decision is answered. "Generalises" means the agent-set decision stays true for its agent and
becomes the fleet rule.

## 9. What this page does not do

- It does not decide anything itself. Every row's content is on the page in "Recorded in",
  with that page's sources; this page carries the id, the gate and the cross-reference.
- It does not hold the agent sets' decisions. Wall-E's 1–52, Eve's E-1..E-20 and Mo's
  M-1..M-11 stay where they are; §8 is an index into them.
- It does not replace the dated decision records (`decisions/2026-09-13-*.md`) for P33 and
  P34; those files are the signatures, this page is the register.
- It does not track build status. Nothing is built; when something is, the register of record
  ([05](05-registry-and-autonomy-contract.md)) and the ladder-state page carry state, not this
  page.
